# Task 1 - 为什么需要隐私？

## 问题

**Q1. Aleo 被定义为首个提供哪三个特性的去中心化应用平台？**

A: Aleo 被定义为首个提供**隐私（Privacy）**、**可编程性（Programmability）**、**高性能（Performance）**三个特性的去中心化应用平台。它是全球首个默认隐私、可编程、高性能的 Layer1 区块链。

---

**Q2. 在去中心化账本中，为什么"重复执行"既是核心优势也是主要弱点？**

A: 
- **作为核心优势**：重复执行（re-execution）确保了所有节点对交易结果达成一致，实现了去信任化（trustless）。任何节点都可以通过重新执行交易来验证其有效性，保证了系统的透明性和可审计性。
- **作为主要弱点**：
  1. **可扩展性问题**：每个节点都必须重新执行每笔交易，使得最弱的节点成为系统瓶颈
  2. **Verifier's Dilemma（验证者困境）**：计算成本高的交易可能让验证者无利可图，导致拒绝验证合法但昂贵的交易
  3. **隐私问题**：所有交易细节（发送方、接收方、金额）完全公开暴露
  4. **资源浪费**：大量重复计算造成巨大的算力浪费

---

**Q3. Aleo 采用的记录模型（Record Model）与传统的账户模型相比，最大的优势是什么？**

A: Record Model 相比传统账户模型的最大优势是**隐私保护**。

具体优势包括：
1. **数据加密**：Record 中的应用程序状态和所有者信息都是加密存储在链上的，而账户模型中账户地址和余额完全公开
2. **并行处理**：Record Model 支持更好的并发性，多个用户可以同时消费不同的 records；而账户模型中同一时间只有一个用户能更新整个程序状态
3. **灵活的状态管理**：Record 可以包含任意数据负载，不仅限于代币余额
4. **UTXO + 账户模型混合**：Aleo 结合了两者的优点——用户资产用 UTXO/Record 模型实现完全隐私，智能合约用账户模型支持全局状态（如 Pool、LP、DEX）

**Q4. Aleo 开发 Leo 语言的初衷（设计目标）是什么？**

A: Leo 语言的设计目标包括：
1. **抽象零知识密码学复杂性**：让开发者无需精通复杂的密码学和电路构建，就能开发隐私应用
2. **默认隐私（Private by Default）**：将隐私作为默认设置，开发者可以像写普通程序一样编写隐私应用
3. **形式化验证**：提供强大的正确性和安全性保证，支持程序的形式化验证
4. **降低开发门槛**：采用类 JavaScript/Rust 的直观语法，让有 Solidity 或 Rust 基础的开发者能快速上手
5. **原生 Aleo 集成**：专为 Aleo 区块链设计，编译为 Aleo Instructions 并在 snarkVM 上运行
6. **抵抗 MEV**：隐私特性使状态转换无需公开披露，抵抗矿工抢先交易和套利攻击

**Q5. 相比其他隐私方案，Aleo 在证明上有哪些显著优势？**

A: Aleo 在证明上的显著优势包括：
1. **链下计算 + 链上验证**：计算在本地（链下）执行，仅将零知识证明提交到链上验证，验证时间与计算复杂度解耦
2. **简洁性（Succinctness）**：验证时间独立于离线计算的复杂度，交易验证时间仅与交易包含的 transition 数量线性相关
3. **可外包证明生成**：用户可以将证明生成委托给第三方证明服务（Prover），使用专用硬件加速
4. **TEE 委托证明**：结合可信执行环境（TEE），在提升性能的同时保护隐私
5. **通用可编程性**：不同于 Zcash 仅支持转账隐私，Aleo 支持任意复杂逻辑的隐私智能合约
6. **AleoBFT 共识**：约 3 秒最终确定性，理论吞吐量可达 125k TPS，交易成本低于 0.01 美元
